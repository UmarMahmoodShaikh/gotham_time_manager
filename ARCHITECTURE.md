## Gotham Time Manager – Architecture and Codebase Guide

This document explains the overall architecture, MVC structure, key modules, request/response flow, and the purpose of the major folders and files in this Phoenix application.

### High-level Overview

- **Phoenix application** using the MVC pattern and contexts.
- **Domain Contexts** under `lib/gotham/` (e.g., `Accounts`) encapsulate business logic and data access using Ecto.
- **Web Layer** under `lib/gotham_time_manager_web/` handles HTTP: router, controllers, JSON views, and plugs.
- **Database** is managed by Ecto via `Gotham.Repo` with migrations in `priv/repo/migrations`.
- **Assets** are built under `assets/` with Tailwind and esbuild; compiled assets live in `priv/static`.
- **Email** is sent via Bamboo with SMTP, configured in `config` and `config/runtime.exs`.

---

## MVC in this App

Phoenix still uses MVC concepts but encourages using Contexts for domain separation. Here is how the parts map in this codebase:

- **Model (Data + Business Logic)**: Ecto schemas and changesets live under `lib/gotham/` (e.g., `Gotham.Accounts.User`). Business logic is in context modules (e.g., `Gotham.Accounts`). The Repo (`Gotham.Repo`) persists data.
- **View (Serialization)**: For APIs, JSON views (e.g., `UserJSON`) render structs and data into JSON. Phoenix 1.7+ generates JSON views as plain modules, often under `lib/..._web/controllers/`.
- **Controller (HTTP)**: Controllers under `lib/gotham_time_manager_web/controllers/` map routes to actions, invoke context functions, and render JSON responses.

### Where things are

- `lib/gotham/accounts/user.ex` – Ecto schema and changeset for users.
- `lib/gotham/accounts.ex` – Accounts context: user CRUD, authentication, token handling integration, and account-specific operations.
- `lib/gotham_time_manager_web/controllers/user_controller.ex` – RESTful API for users (index/show/create/update/delete) calling into `Accounts`.
- `lib/gotham_time_manager_web/controllers/auth_controller.ex` – Sign up/in/out endpoints and token issuance.
- `lib/gotham_time_manager_web/router.ex` – The route definitions that connect URLs to controllers/actions.
- `lib/gotham/mailer.ex` – Bamboo mailer.
- `lib/gotham/user_email.ex` – Email builders (e.g., onboarding email).

## Request Flow: Example API Calls

### Sign up (user creation + onboarding email)
1. Client calls `POST /api/sign_up` with payload containing `personal_email`, `first_name`, `last_name`, `username`, etc.
2. `GothamWeb.AuthController.sign_up/2` validates expected params and calls `Gotham.Accounts.create_user/1`.
3. In `Accounts.create_user/1`:
   - A corporate email `first_name.last_name@gotham.com` is generated when not provided.
   - A 6-digit password is generated when not provided.
   - The `User` changeset is built and inserted via `Gotham.Repo.insert/1`.
   - On success, an onboarding email is sent via `Gotham.UserEmail.onboard_user/2` and `Gotham.Mailer.deliver/1`.
4. The controller returns a JSON response with the created user attributes and a token generated by `Accounts.generate_token/1`.

### Sign in (JWT issuance)
1. Client calls `POST /api/sign_in` with `email` and `password`.
2. `GothamWeb.AuthController.sign_in/2` calls `Accounts.authenticate_user/2`.
3. If valid, a JWT is generated (`Accounts.generate_token/1`), and the response includes `meta.token`.

### Users API (typical CRUD)
- `GothamWeb.UserController` exposes REST endpoints.
- Each action calls into `Gotham.Accounts` (e.g., `Accounts.list_users/0`, `Accounts.update_user/2`).
- JSON is rendered using the corresponding JSON view module referenced by the controller (e.g., `render(:show, user: user)`).

## Purpose of Key Files

### User-related files
- `lib/gotham/accounts/user.ex`
  - Ecto schema for the `users` table.
  - Fields include: `email` (corporate), `personal_email`, `phone`, `first_name`, `last_name`, `password_hash`, virtual `password`, `is_active`, `is_visually_challenged`, and `role_id`.
  - Changeset handles casting, validation, default role, and password hashing through Bcrypt.

- `lib/gotham/accounts.ex` (Accounts Context)
  - Defines the public API for working with users, roles, permissions.
  - `create_user/1` encapsulates corporate email/password generation and onboarding email delivery.
  - `authenticate_user/2` checks credentials.
  - Token helpers delegate to `Gotham.Token`.
  - Contains CRUD for users, roles, and permissions.

- `lib/gotham_time_manager_web/controllers/user_controller.ex`
  - HTTP endpoints for user resources (index/create/show/update/delete).
  - Authorizes actions where needed and renders JSON responses.

- `lib/gotham_time_manager_web/controllers/auth_controller.ex`
  - `sign_up/2`: creates a user and returns a token (and triggers onboarding email via context).
  - `sign_in/2`: authenticates and returns a JWT.
  - `sign_out/2`: a stateless no-op (client discards token).

- `lib/gotham_time_manager_web/controllers/user_json.ex` (or similar JSON view module)
  - Serializes user structs to API-friendly JSON maps.
  - Used by controllers via `render(:show, user: user)` or `render(:index, users: users)`.

### Email files
- `lib/gotham/mailer.ex`
  - Bamboo Mailer definition (`use Bamboo.Mailer, otp_app: :gotham`).

- `lib/gotham/user_email.ex`
  - Email builder module using `Bamboo.Email` helpers.
  - `onboard_user/2` generates a welcome email sent to `personal_email` with the corporate email and temporary password.

### Repo and Database
- `lib/gotham/repo.ex` (implicit; generated in Phoenix apps)
  - Ecto repository configuration used by contexts to interact with the database.

- `priv/repo/migrations/*.exs`
  - Database migrations (definitions of schema changes).
  - Example: `create_users` migration defines columns and indexes; subsequent migrations add fields like `personal_email`, `phone`, `is_active`.

## What is `Gotham` vs `GothamWeb`?

- `Gotham` (under `lib/gotham/`)
  - The core domain and business logic layer.
  - Contains contexts (e.g., `Accounts`), schemas (e.g., `Accounts.User`), and services (e.g., `Mailer`, `UserEmail`).
  - Should not know about HTTP details.

- `GothamTimeManagerWeb` (under `lib/gotham_time_manager_web/`)
  - The web interface layer.
  - Contains `router.ex`, controllers, JSON views, endpoint, and web-specific helpers.
  - Calls into `Gotham` contexts to perform work.

## Folder-by-Folder Purpose

### `lib/`
- `lib/gotham/` – Domain layer (contexts, schemas, services):
  - `accounts/` – User, Role, Permission schemas and related logic.
  - `accounts.ex` – Public API for the Accounts domain.
  - `mailer.ex` – Email sending via Bamboo.
  - `user_email.ex` – Email builders.
  - Other domain modules (e.g., token helpers) when present.

- `lib/gotham_time_manager_web/` – Web layer:
  - `router.ex` – Route definitions map paths to controllers.
  - `controllers/` – HTTP controllers (`AuthController`, `UserController`, etc.).
  - `endpoint.ex` – Phoenix endpoint configuration and plugs pipeline.
  - JSON views (e.g., `user_json.ex`) – shape API responses.

### `config/`
- `config.exs` – Base app configuration (endpoint, mailers in dev/test, assets).
- `dev.exs`, `test.exs`, `prod.exs` – Environment-specific compile-time config.
- `runtime.exs` – Runtime config for all envs (especially production secrets like database URL and SMTP); sets Bamboo SMTP adapter via env vars.

### `priv/`
- `repo/migrations/` – Database schema migrations.
- `gettext/` – Translation files if i18n is used.
- `static/` – Compiled/static assets (images, js, css) served by the endpoint.

### `assets/`
- `js/`, `css/` – Frontend entrypoints (Phoenix default bundles: `app.js` and `app.css`).
- Built with Tailwind v4 and esbuild per the project’s guidance.

### `test/`
- ExUnit tests for contexts and controllers.
- Uses `Phoenix.LiveViewTest` for LiveView (if any), and controller tests for JSON APIs.

## Database Schema & Changesets

- Schemas define table structure and field types.
- Changesets validate and transform incoming data before persistence.
- The `User` schema includes a virtual `password` field and persists `password_hash` using Bcrypt.
- `User` changeset also sets default role IDs and enforces uniqueness constraints.

---

## Routing

- Located in `lib/gotham_time_manager_web/router.ex`.
- Defines pipelines (e.g., `:api`) and scopes (e.g., `/api`).
- Maps HTTP verbs and paths to controller actions.
- Example: `post "/sign_up", AuthController, :sign_up`.

---

## Authentication & Tokens

- `Accounts.authenticate_user/2` verifies credentials.
- `Accounts.generate_token/1` signs a JWT (via `Gotham.Token`).
- Controllers use the generated token in responses.

---

## Emails & SMTP

- In dev/test, `Gotham.Mailer` uses `Bamboo.LocalAdapter` per `config/config.exs`.
- In production, `Gotham.Mailer` uses `Bamboo.SMTPAdapter` per `config/runtime.exs` and SMTP env vars:
  - `SMTP_SERVER`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_HOSTNAME`.
- `Gotham.UserEmail.onboard_user/2` is used by `Accounts.create_user/1` to send onboarding details.

---

## Components and LiveView (if added later)

- Reusable UI components would live under `lib/gotham_time_manager_web/components/` and be imported where needed.
- LiveViews follow the `...Web.SomeLive` naming and are routed with the `live` macro; this codebase primarily exposes JSON APIs currently.

## Quick Reference – How a User is Created and Emailed

1. Request hits `AuthController.sign_up/2`.
2. `Accounts.create_user/1` generates corporate email and a 6-digit password if not provided.
3. `User` changeset validates and hashes password.
4. `Repo.insert/1` persists the user.
5. `UserEmail.onboard_user/2` builds the email; `Mailer.deliver/1` sends via Bamboo/SMTP.
6. Controller returns JSON with a signed token from `Accounts.generate_token/1`.
